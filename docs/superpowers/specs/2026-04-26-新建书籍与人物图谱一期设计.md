# 新建书籍与人物图谱一期设计

日期：2026-04-26

范围：
- `新建书籍` 独立创建页
- `设定页 /world` 的实体维护能力增强
- `人物图谱 /graph` 独立关系页
- 为上述能力服务的数据模型与提交链路

目标：
- 让用户可以创建真实书籍项目，而不是只依赖 demo 数据
- 在建书时一次性录入常见立项信息与少量人物种子
- 建书完成后立即得到一份非空的人物 / 势力 / 地点关系图谱
- 让图谱默认适合查阅，同时保留低摩擦编辑能力

## 1. 项目拆分与第一期范围

当前用户需求包含四个方向：
- 新建书籍时支持完整基础信息
- 增加人物图谱相关功能
- 增加文笔风格投喂模块
- 增加根据设定自动查找资料的功能

为了避免 spec 过大、实现范围失控，本轮只做第一期：
- `新建书籍`
- `人物图谱`

后续独立子项目建议：
- 第二期：`文笔风格投喂`
- 第三期：`根据设定自动查找资料`

这样拆分的原因：
- 新建书籍与人物图谱有直接数据流关系，天然适合一起做
- 文风投喂与资料检索都涉及新的 AI 工作流和数据结构，独立成下一轮更稳
- 第一阶段先解决“项目从何创建”和“图谱为什么不是空白”两个根问题

## 2. 设计方向

本期采用：
- `独立新建书籍页`
- `混合型图谱入口`
- `平衡型图谱交互`
- `人物 + 势力 + 地点` 三类实体关系图

核心理念：
- 建书过程不做成沉重策划问卷
- 但也不能只填标题和 premise 就结束
- 图谱不是绘图工具优先，而是写作工作流优先
- 查阅应是默认态，编辑应是低摩擦入口

## 3. 信息架构

第一期新增或调整后的工作区结构：

- `/novels`：作品入口页
- `新建书籍页`：独立创建页
- `/novels/[novelSlug]/world`：设定维护页
- `/novels/[novelSlug]/graph`：独立图谱页

职责划分：

`新建书籍页`
- 完成立项信息录入
- 初始化人物、势力、地点种子
- 可选初始化部分关系

`/world`
- 作为日常维护入口
- 维护人物、势力、地点列表与详情
- 提供明确的 `打开图谱` 入口

`/graph`
- 用于查看、筛选、理解和编辑实体关系
- 重点承接建书阶段初始化的实体与关系

## 4. 新建书籍页设计

新建书籍采用独立页面，不使用弹窗。

原因：
- 这类信息量已经超过轻量弹窗的合理承载范围
- 后续会继续扩展，不适合塞进模态框
- 独立页面更适合做表单分区、AI 辅助与初始化逻辑

### 4.1 页面结构

页面分为三段：

1. `基础信息`
2. `扩展策划`
3. `人物种子`

### 4.2 基础信息

基础信息用于完成最小立项，建议字段包括：
- 书名
- 类型 / 大类
- 细分类型
- 目标受众
- 一句话 premise
- 叙事视角
- 故事结构

故事结构选项可参考常见创作产品：
- 三幕结构
- 英雄之旅
- 节拍表
- 起承转合
- 多线叙事
- 自由结构

### 4.3 扩展策划

扩展策划作为强化信息层，建议字段包括：
- 总章数
- 每章字数
- 世界观 / 初始设定
- 语气 / 文风目标

设计原则：
- 允许认真立项的用户一次性补全更多信息
- 但不强迫所有用户在首次创建时填满全部字段

### 4.4 人物种子

建书时可录入 `1 到 3 个` 核心人物，避免进入工作区后图谱为空。

每个人物建议字段：
- 姓名
- 身份 / 角色定位
- 简述
- 所属势力
- 关键地点

可选能力：
- 直接设置人物之间的初始关系
- 若填写了新的势力或地点，自动生成对应实体

### 4.5 交互原则

- 核心立项字段默认直接展开
- 扩展策划可见但不应造成压迫感
- 人物种子要支持快速添加与快速跳过
- 提交成功后直接进入新作品工作区
- 图谱、设定页和工作区总览都应已有初始化数据

## 5. 设定页 /world 设计

`/world` 在第一期中的角色不是图谱页替代品，而是日常维护入口。

### 5.1 页面职责

- 展示人物列表
- 展示势力列表
- 展示地点列表
- 支持新增、编辑、删除实体
- 提供 `打开图谱` 的明确入口

### 5.2 使用场景

高频场景是：
- 快速查某个角色资料
- 修改人物设定
- 补充某个势力或地点
- 从列表跳到图谱查看关系

因此 `/world` 应保持：
- 列表清晰
- 搜索方便
- 详情编辑直接

而不承担：
- 全部图谱交互
- 复杂关系绘制主舞台

## 6. 独立图谱页 /graph 设计

### 6.1 图谱定位

图谱页采用 `平衡型` 方案：
- 默认更适合查阅
- 但所有节点和关系都能快速进入编辑

不做成：
- 纯展示页
- 纯拖拽绘图工具

### 6.2 第一阶段实体范围

第一期图谱只覆盖三类实体：
- 人物
- 势力
- 地点

不在本期范围：
- 物品
- 规则
- 事件
- 全量设定知识图谱

### 6.3 第一阶段关系范围

第一期关系包括：
- 人物 ↔ 人物
- 人物 ↔ 势力
- 人物 ↔ 地点

这能覆盖大多数小说写作中最先要看的关系网络。

### 6.4 页面结构

建议采用三栏：

左侧：
- 搜索
- 筛选
- 实体列表

中间：
- 图谱画布
- 节点与连线展示

右侧：
- 节点详情
- 关系详情
- 快速编辑表单

### 6.5 交互方式

默认行为：
- 点击节点：高亮关联节点和连线
- 点击关系：显示关系详情
- 列表与图谱联动

编辑行为：
- 在右侧面板中编辑节点信息
- 在右侧面板中编辑关系类型、描述、备注
- 不要求用户离开图谱页进入其他页面才能改资料

### 6.6 平衡型交互原则

为了避免图谱过重，第一期不主打复杂拖拽创作，而主打：
- 快速理解人物网络
- 快速定位相关势力与地点
- 快速修正关系

也就是说：
- 查阅是默认态
- 编辑是低摩擦入口
- 复杂排版不是第一期目标

## 7. 数据模型方向

### 7.1 `Novel` 扩展字段

现有 `Novel` 需要补充更多立项信息，建议新增：
- `category`：大类 / 类型
- `subGenre`：细分类型
- `targetAudience`：目标受众
- `narrativeView`：叙事视角
- `storyStructure`：故事结构
- `plannedChapterCount`：规划总章数
- `targetWordsPerChapter`：每章目标字数
- `styleGoal`：目标语气 / 文风方向
- `worldSeed`：世界观初设

这些字段服务于：
- 新建书籍页的立项信息
- 后续 AI 写作策略
- 图谱和设定页的上下文补充

### 7.2 `StoryEntity` 扩展方向

现有 `StoryEntity` 已具备良好基础。

第一期重点强化：
- `CHARACTER`
- `FACTION`
- `LOCATION`

人物相关可补充的 profile 内容建议包括：
- 身份 / 角色定位
- 外显标签
- 简述
- 所属势力
- 关键地点

其中一部分可继续保存在 `profile` 中，以避免第一期过度拆字段。

### 7.3 `EntityRelation` 使用增强

现有 `EntityRelation` 结构已经能承载第一期关系。

第一期重点不是彻底重构关系表，而是：
- 真正把它接入前端录入与编辑流程
- 让人物 ↔ 人物、人物 ↔ 势力、人物 ↔ 地点关系都能落盘
- 提供关系描述与备注的前端编辑能力

### 7.4 建书到图谱的数据流

建书提交时的数据流：

1. 创建 `Novel`
2. 写入基础立项字段
3. 创建人物种子实体
4. 如有势力 / 地点则创建对应实体
5. 如有初始关系则写入 `EntityRelation`
6. 跳转到新作品工作区

结果：
- `/world` 不是空的
- `/graph` 不是空的
- 用户刚建完书就能开始在真实上下文中继续工作

## 8. 错误处理与一致性

第一期最容易出问题的地方有三类：
- 建书字段不完整
- 初始关系绑定到不存在的实体
- 设定页、图谱页与数据库的数据不同步

### 8.1 表单校验

- 核心字段缺失时禁止提交
- 扩展字段允许部分为空
- 人物种子可以最小化录入，不要求一次写很全

### 8.2 关系合法性

- 初始关系必须绑定真实已创建实体
- 不允许悬空关系
- 删除实体时要同步处理相关关系，或明确提示用户

### 8.3 数据同步

- `/world` 与 `/graph` 必须读取同一份实体与关系数据
- 图谱中的编辑结果应立即体现在设定列表中
- 列表中的编辑结果应立即体现在图谱详情中

## 9. 验证标准

第一期完成后，至少应满足：

- 用户可以通过独立建书页创建一本新书
- 建书时可以填写常见立项信息，而不仅是标题和 premise
- 建书完成后，作品已有初始人物 / 势力 / 地点数据
- `/world` 可以看到并维护这些实体
- `/graph` 可以展示人物、势力、地点之间的关系
- 图谱默认适合查阅，但节点和关系都可低摩擦编辑
- 图谱不是空白页，能承接建书时输入的种子数据

## 10. 实施顺序建议

推荐开发顺序：

1. 扩展 `Novel` 与实体相关数据模型
2. 完成 `新建书籍` 独立创建页与提交链路
3. 在建书流程里接入人物种子与初始关系写入
4. 升级 `/world` 让人物 / 势力 / 地点可维护
5. 新增 `/graph` 独立图谱页
6. 最后补测试、空状态、删除/编辑边界

这样排序的原因：
- 先把数据能真实创建出来
- 再让设定页和图谱页消费这份真实数据
- 避免先做页面壳子、后补真实数据导致大量返工

## 11. 第一阶段明确不做

为了控制范围，第一期不做：
- 自动从正文抽取人物关系
- 图谱拖拽排版保存
- 复杂力导向布局自定义
- 文笔风格投喂训练
- 根据设定自动查找资料
- AI 自动生成完整人物网或世界设定库

这些功能后续可以继续做，但不应混入本期实现。

## 12. 风险与注意事项

- 如果建书页字段过多，会把首次创建流程做得过重
- 如果人物种子录入过弱，图谱页会重新变成空壳
- 如果图谱过度强调编辑，会偏离写作产品调性
- 如果 `/world` 与 `/graph` 使用不同数据组织方式，后续同步成本会迅速上升

本期最重要的不是“图谱炫不炫”，而是：
- 新书创建能否真实落地
- 图谱是否从第一天就不是空的
- 设定维护与关系理解能否形成一条顺畅链路
