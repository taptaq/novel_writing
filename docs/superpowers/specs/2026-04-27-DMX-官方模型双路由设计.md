# DMX 与官方模型双路由设计

## 背景

当前项目已经具备按模型按钮临时切换的 AI 写作能力，并且主路由已迁移到 DMX 与官方 DeepSeek 的混合结构。

新的目标是：

- 保持前端模型选择尽量简洁，不增加“渠道”按钮
- 对 `Kimi`、`GLM`、`Qwen` 增加“DMX 优先，官方兜底”的双路由
- `Mimo` 继续仅使用 DMX
- `DeepSeek` 继续保留独立按钮，但不走 DMX，直接走官方，再落到系统兜底
- 当 DMX 或官方上游异常时，系统仍可继续使用统一的 fallback 模型完成请求

## 用户可见行为

前端模型选择维持现状，不新增额外按钮：

- 自动
- Kimi
- GLM
- Mimo
- Qwen
- DeepSeek
- 系统兜底

用户在手动选择模型时，不需要理解渠道来源。系统会在后端按照该模型对应的优先级依次尝试，直到成功或所有候选失败。

## 路由规则

### 自动模式

自动模式按以下顺序尝试：

1. DMX Kimi
2. Kimi 官方
3. DMX GLM
4. GLM 官方
5. DMX Mimo
6. DMX Qwen
7. Qwen 官方
8. DeepSeek 官方
9. 系统兜底

这样可以优先消化 DMX 的聚合能力，同时在某个供应商异常时仍然保留对应官方接口与最终兜底链路。

### 手动模式

每个按钮对应自己的候选链：

- `Kimi`：`DMX Kimi -> Kimi 官方 -> fallback`
- `GLM`：`DMX GLM -> GLM 官方 -> fallback`
- `Qwen`：`DMX Qwen -> Qwen 官方 -> fallback`
- `Mimo`：`DMX Mimo -> fallback`
- `DeepSeek`：`DeepSeek 官方 -> fallback`
- `系统兜底`：仅 fallback

这里的关键点是：手动模式不再等价于“只打一个上游”，而是“固定模型意图下的多渠道重试”。

## 配置设计

### 保留的现有配置

- `DMX_API_KEY`
- `DMX_BASE_URL`
- `DMX_MODEL_KIMI`
- `DMX_MODEL_GLM`
- `DMX_MODEL_MIMO`
- `DMX_MODEL_QWEN`
- `DEEPSEEK_API_KEY`
- `DEEPSEEK_BASE_URL`
- `DEEPSEEK_MODEL`
- `LLM_API_KEY`
- `LLM_BASE_URL`
- `LLM_MODEL`

### 新增的官方模型配置

- `KIMI_API_KEY`
- `KIMI_BASE_URL`
- `KIMI_MODEL`
- `GLM_API_KEY`
- `GLM_BASE_URL`
- `GLM_MODEL`
- `QWEN_API_KEY`
- `QWEN_BASE_URL`
- `QWEN_MODEL`

默认值策略：

- `KIMI_BASE_URL`、`GLM_BASE_URL`、`QWEN_BASE_URL` 默认采用各自官方 OpenAI 兼容地址
- `KIMI_MODEL`、`GLM_MODEL`、`QWEN_MODEL` 使用当前稳定可用的默认模型名
- 如果未配置某个官方 key，则该官方 provider 在自动模式下被跳过，在手动模式下只要前序 provider 可用仍继续工作

## 后端结构设计

### env 层

在 `src/lib/env.ts` 中新增官方 Kimi / GLM / Qwen 的读取逻辑，并扩展 `isAiConfigured` 判定，让以下任一配置存在即可视作 AI 可用：

- 任一 DMX key
- 任一官方模型 key
- fallback key

### provider 层

当前 `getOrderedProviders()` 返回的是一维 provider 列表。为了支持“同一模型选择下的多 provider 候选”，需要把 provider 结构升级为：

- `selection`：用户选择的模型按钮
- `provider`：真实上游标识，例如 `dmx-kimi`、`official-kimi`
- `model` / `baseUrl` / `apiKey`
- `temperature` / `topP`
- `priority`：同一 selection 内部的尝试顺序

自动模式直接按全局优先顺序遍历。
手动模式筛出同一 `selection` 的所有 provider，并按优先级依次尝试，最后再接 `fallback`。

### router 层

`callRoutedJsonModel()` 需要调整为：

- `auto`：遍历完整 provider 序列
- 手动模型：遍历该模型的 provider 序列，再补上 `fallback`
- `fallback`：仅走 fallback

错误聚合保留当前模式，但要记录真实 provider 名称，而不是只记录 selection，这样日志和调试更有用。

### meta 返回

保留当前接口结构，不新增用户必须理解的新字段。

继续返回：

- `requestedModel`
- `resolvedProvider`
- `resolvedModel`
- `usedFallback`

其中 `resolvedProvider` 会出现：

- `dmx-kimi`
- `official-kimi`
- `dmx-glm`
- `official-glm`
- `dmx-mimo`
- `dmx-qwen`
- `official-qwen`
- `deepseek-official`
- `fallback`

## 前端设计

前端按钮、下拉选项与交互保持不变，不额外暴露“DMX / 官方”渠道概念。

唯一需要保留的是结果区域里对 `resolvedModel` 与 `usedFallback` 的展示，帮助用户和开发者判断当前是否触发了兜底。

如果后续希望更明显地区分渠道，可以在不增加按钮数量的前提下，把“本次使用”文案扩成“本次使用：official-kimi / moonshot-v1-xxx”这类格式，但这不是本次必须项。

## 错误处理

- 某个 provider 缺少 `apiKey`、`baseUrl` 或 `model` 时，自动模式跳过，手动模式继续尝试同 selection 的下一个 provider
- 只有当该 selection 的全部 provider 与 fallback 均失败时，才向上抛出错误
- 聚合错误中需要包含 provider 名和失败原因，便于定位是 DMX 问题还是官方问题

## 测试策略

至少覆盖以下场景：

- 自动模式下按新顺序依次尝试
- `Kimi` 手动模式下 `DMX -> 官方 -> fallback`
- `GLM` 手动模式下 `DMX -> 官方 -> fallback`
- `Qwen` 手动模式下 `DMX -> 官方 -> fallback`
- `Mimo` 手动模式下 `DMX -> fallback`
- `DeepSeek` 手动模式下 `官方 -> fallback`
- 缺失官方 key 时自动跳过
- 缺失 DMX key 时手动模型仍可落到官方
- 前端模型选项保持不变

## 风险与约束

- 不同官方模型的 OpenAI 兼容程度可能不同，默认参数需保持克制，避免携带不兼容字段
- 如果官方模型名未来变化，需要只改环境变量而不是改代码常量
- 当前工程不是 git 工作树，本次规格文件无法按流程提交，只能先写入本地文档目录

## 实施范围

本次只做路由与配置层增强，不做以下内容：

- 新增前端渠道按钮
- 新增模型管理后台
- 新增实时健康检查面板
- 新增上游配额监控

## 验收标准

- 用户界面按钮数量与名称符合当前设计
- 各模型能按既定顺序自动回退
- `DeepSeek` 保持官方独立入口
- `.env.example` 补齐所有新增官方配置
- 测试、类型检查、构建全部通过
