# 英伟达优先模型路由与临时选择设计

日期：2026-04-26

范围：
- 为当前项目建立统一的 AI 模型路由层
- 默认优先使用英伟达模型
- 支持在具体 AI 功能面板里临时切换模型
- 保留现有自有模型作为最终兜底

目标：
- 让全项目所有 AI 调用遵循同一套模型优先级
- 在不改业务逻辑的前提下统一接入多模型回退
- 给用户一个明确、直接可见的模型选择入口
- 把真实密钥保留在环境变量中，不写死在源码里

## 1. 需求结论

用户已明确确认以下产品与实现约束：

- 全项目所有模型调用都要统一走这一套路由，不只限于 `/api/ai/assist`
- 英伟达模型优先顺序固定为：
  - `Kimi`
  - `GLM`
  - `DeepSeek`
  - `Qwen`
  - `现有自有模型兜底`
- 支持在每个具体功能面板里临时切换模型
- 模型选择器默认直接显示，不收进高级选项
- 当用户手动指定模型时：
  - 只调用该模型
  - 失败直接报错
  - 不自动切换其他模型
- 当用户选择 `自动` 时：
  - 才启用完整优先级回退链
- 英伟达 key 与模型配置通过环境变量管理

## 2. 设计方向

本次采用：

- `统一后端路由层`
- `前端只传简单模型选择值`
- `自动模式启用优先级回退`
- `手动模式严格指定，不做自动回退`

不采用：

- 前端直接拼装不同厂商请求体
- 每个业务模块单独写一套回退逻辑
- 全局持久化模型选择

原因：

- 当前项目已经有 AI 调用入口，后端集中路由最利于后续扩展
- 不同厂商的参数细节、thinking 开关、响应格式差异都应该藏在统一层里
- 用户已经明确要“每次在具体功能里临时切换”，不适合做全局共享状态

## 3. 信息架构与调用链

新增后的调用链：

- 前端功能面板
  - 例如 `章节写作面板`
  - 负责展示模型选择器
  - 负责提交 `modelSelection`
- API 层
  - 接收业务请求与 `modelSelection`
  - 不直接绑定具体模型
- AI 路由层
  - 解释选择值
  - 执行自动回退或严格指定
  - 屏蔽各模型请求差异
- 业务层
  - 只处理 prompt、业务输入与业务结果
  - 不承担模型路由逻辑

## 4. 模型路由设计

### 4.1 路由模式

统一路由层接收：

- `messages`
- `responseMode`
  - 本期至少覆盖当前 `JSON` 型返回场景
- `modelSelection`

### 4.2 modelSelection 值域

前后端统一使用以下值：

- `auto`
- `kimi`
- `glm`
- `deepseek`
- `qwen`
- `fallback`

### 4.3 自动模式规则

当 `modelSelection = auto` 时：

1. 尝试 `Kimi`
2. 失败后尝试 `GLM`
3. 失败后尝试 `DeepSeek`
4. 失败后尝试 `Qwen`
5. 前四者都失败后，尝试现有 `LLM_*` 自有模型兜底

这里的“失败”包括：

- 缺少必要配置
- 网络错误
- 非 2xx HTTP
- 空响应
- 返回内容无法按预期解析

自动模式下，单个模型失败不立即中断整体请求，而是继续进入下一项。

### 4.4 手动模式规则

当 `modelSelection` 为具体模型时：

- `kimi`：只调用 Kimi
- `glm`：只调用 GLM
- `deepseek`：只调用 DeepSeek
- `qwen`：只调用 Qwen
- `fallback`：只调用现有自有模型

手动模式下：

- 失败直接返回错误
- 不再自动尝试其他模型

### 4.5 返回结果统一化

路由层对外输出统一结果结构：

- `content`
- `provider`
- `model`
- `usedFallback`
- `reasoning?`

其中：

- `provider` 表示实际命中的提供方
- `model` 表示实际命中的模型名
- `usedFallback` 表示是否落到了最终自有模型兜底
- `reasoning` 仅在部分支持 reasoning 的模型返回且当前场景需要保留时使用

## 5. 提供者配置层设计

新增一个专门的 provider 配置层，负责定义每个模型的静态配置：

- 提供者标识
- 模型名
- base URL
- API Key 来源
- 默认采样参数
- 是否启用 thinking
- 请求体差异映射

## 6. 环境变量设计

新增环境变量：

- `NVIDIA_API_KEY`
- `NVIDIA_BASE_URL`
- `NVIDIA_MODEL_KIMI`
- `NVIDIA_MODEL_GLM`
- `NVIDIA_MODEL_DEEPSEEK`
- `NVIDIA_MODEL_QWEN`

保留现有环境变量：

- `LLM_API_KEY`
- `LLM_BASE_URL`
- `LLM_MODEL`

默认建议值：

- `NVIDIA_BASE_URL=https://integrate.api.nvidia.com/v1`
- `NVIDIA_MODEL_KIMI=moonshotai/kimi-k2.5`
- `NVIDIA_MODEL_GLM=z-ai/glm-5.1`
- `NVIDIA_MODEL_DEEPSEEK=deepseek-ai/deepseek-v4-pro`
- `NVIDIA_MODEL_QWEN=qwen/qwen3.5-397b-a17b`

真实密钥处理原则：

- 真正的 `NVIDIA_API_KEY` 只写入本地环境文件
- 不写进源码
- 不写进测试
- 不写进 spec 文档

本轮会补充：

- `.env.example` 占位示例
- 本地运行所需环境变量读取逻辑

## 7. 前端交互设计

### 7.1 展示方式

模型选择器默认直接显示在具体 AI 功能面板中，不折叠，不藏在高级设置里。

第一期先接入：

- 当前章节写作功能面板

后续其他 AI 面板复用同一模式。

### 7.2 选项文案

建议前端文案：

- `自动`
- `Kimi`
- `GLM`
- `DeepSeek`
- `Qwen`
- `系统兜底`

默认值：

- `自动`

### 7.3 结果回显

每次返回结果后，前端应能展示：

- 本次请求的是哪种模式
- 最终实际命中了哪个模型

例如：

- `本次使用：Kimi`
- `本次使用：系统兜底`

这样用户在自动模式下也能知道本次到底落到了谁。

## 8. API 契约调整

以当前 `/api/ai/assist` 为例，入参新增：

- `modelSelection`

值域：

- `auto | kimi | glm | deepseek | qwen | fallback`

返回结构在原有业务结果外新增 `meta`：

- `requestedModel`
- `resolvedProvider`
- `resolvedModel`
- `usedFallback`

后续所有 AI 接口如果有模型调用，也应沿用同样模式，避免接口风格分裂。

## 9. 错误处理策略

### 9.1 自动模式

- 单模型失败不立刻报错
- 继续尝试下一个
- 记录失败原因用于最终日志与调试
- 全部失败后才向业务层抛出整体失败

### 9.2 手动模式

- 只调用用户指定模型
- 失败立即返回错误
- 不做自动切换

### 9.3 缺失配置

自动模式：

- 某个模型缺配置时直接跳过

手动模式：

- 如果用户指定了缺配置模型，直接返回“该模型未配置”

### 9.4 解析失败

如果某模型返回内容不符合当前调用模式预期：

- 自动模式：视为该模型失败，继续下一项
- 手动模式：直接返回错误

## 10. 兼容性与当前项目改动边界

本次不会重写整个 AI 业务层，只做最小必要接入：

- 统一路由层落在 `src/lib/ai/`
- 现有 `writing-engine.ts` 接到统一路由
- 现有 `chapter-composer.tsx` 增加模型选择
- 现有 `/api/ai/assist` 入参与返回结构扩展

当前项目里尚未接入其他 AI 场景的地方，本次只为后续复用铺路，不额外扩展无关能力。

## 11. 测试策略

本期至少补以下测试：

- 路由层单测
  - `auto` 时按顺序尝试
  - 自动模式遇到失败会继续
  - 手动模式失败不回退
  - 缺配置模型在自动模式会被跳过
  - `fallback` 手动模式只走现有模型
- API 单测
  - `/api/ai/assist` 能接收 `modelSelection`
  - 错误时返回正确消息
- 组件测试
  - 写作面板默认展示模型选择器
  - 默认选中 `自动`
  - 结果区域可显示最终命中的模型

## 12. 风险与非本期范围

已知风险：

- 不同英伟达模型对 reasoning 字段、thinking 参数、流式返回细节支持并不完全一致，需要在路由层单独兼容
- 现有 JSON 提取策略较简单，某些模型即使返回成功也可能需要更稳健的解析

非本期范围：

- 模型使用统计面板
- 多功能面板共享最近一次模型选择
- 针对不同写作模式定制不同优先链
- 全量流式输出重构

## 13. 实施建议

建议按以下顺序实施：

1. 扩展环境变量读取
2. 建立 provider 配置层与统一路由层
3. 把现有 `callJsonModel` 接到新路由
4. 扩展 `/api/ai/assist` 入参与响应元信息
5. 在写作面板加模型选择器与结果回显
6. 补测试并验证自动 / 手动两种路径
